# 艺起搭：从页面原型到可用衣橱

2026-09-17。目标用户是有日常校园穿搭需求的学生，目标是将自己的衣物录入、组合、记录并再次使用。比赛演示应展示这条真实链路。保留当前 ArkTS / ArkUI Stage、API 26、phone、本地保存的工程条件，不据未知截止日期削减质量。

## 三种视角的候选方案

| 视角 | 候选 | 要解决的问题 |
| --- | --- | --- |
| 产品 | 多图录入队列 | 首次建立衣橱逐件操作太慢 |
| 产品 | 一周校园穿搭计划 | 从偶尔打开变成连续使用 |
| 产品 | 闲置衣物唤醒 | 已有衣物利用率低 |
| 产品 | 收藏与负反馈推荐 | 推荐不随实际使用改善 |
| 产品 | 可编辑、可分享的搭配作品 | 用户投入的创作缺少可带走的结果 |
| 设计 | 拖动、缩放、旋转的自由画布 | 固定品类列表不能表达搭配意图 |
| 设计 | 原图与抠图对照确认 | 处理效果不可靠时用户失去控制 |
| 设计 | 多图逐件确认、失败重试 | 批量任务结果容易混淆 |
| 设计 | 日历、衣物次数、记录互相跳转 | 统计缺少可追溯依据 |
| 设计 | 场合模板与画布配色 | 空白画布创作门槛高 |
| 工程 | 端侧主体分割能力探测与降级 | 设备能力差异和云服务缺失 |
| 工程 | 归一化画布布局与稳定作品 ID | 重开丢失布局、重复保存生成副本 |
| 工程 | PNG 导出与系统分享 | 目前分享只有文字清单 |
| 工程 | 统一穿着记录变更函数 | 手动日记、反馈、删除计数不一致 |
| 工程 | 卡片读取已验证方案 | 系统入口必须与应用内状态一致 |

## 优先五项

| 顺序 | 方案与一句话定义 | 选择原因 | 待验证假设与实验 |
| --- | --- | --- | --- |
| 1 | 自由搭配作品：拖动、缩放、旋转、层级、撤销、保存再编辑、图片导出 | 不依赖云端服务，能直接形成用户可保存的作品 | 小屏手势是否顺手；在手机上调整三件衣物，保存重启后比较布局与导出图 |
| 2 | 真实录入：多图确认队列与可撤回的主体抠图 | 直接改善建立个人衣橱的成本，也是画布素材来源 | 主体分割是否能提取衣物而非整个人；分别测试平铺、衣架、上身照及设备不支持时的行为 |
| 3 | 可追溯穿着统计：统一新增、修改、去重与删除 | 数据可信度是后续推荐与闲置统计的基础 | 同日同组合只记录一次是否符合需求；以跨入口重复、编辑换衣物和删除回退验证 |
| 4 | 推荐反馈：明确喜欢、少推荐及近期穿着权重 | 让推荐体现个人使用积累 | 用同一衣橱比较反馈前后排序，同时证明待洗、温度等约束仍有效 |
| 5 | 今日计划与桌面卡片：确定今天的一套并同步系统入口 | 将原生能力落在真实场景 | 真机冷/热启动、修改方案、卡片更新；互动和摇动以设备实测为准 |

首批实施自由画布与记录一致性，录入能力先核实 SDK 与设备边界。AI 试穿、云同步和付费会员暂不计入已交付能力。自动分类需要真实模型及可靠性验证，不根据文件名或固定默认值声称识别成功。
