# Index.ets 编码事故：恢复依据与未确定项

编写日期：2026-09-17。本文件记录一次由实现过程造成的文件损坏、恢复依据、以及**无法证明**的部分。
结论先行：**这不是原文恢复**。文件可编译、可运行、结构、状态与动画保留，
但 326 处中文字符的原始字节已被销毁，其中相当一部分只能按上下文补写，不能称为"与原文逐字一致"。

## 1. 事故经过

- 我在批量修改一处调用点时，用 `Get-Content` / `Set-Content -Encoding UTF8` 做了整文件替换。
- 本机 Windows PowerShell 5.1 的 `Get-Content` 默认按 CP936（GBK）解码，而文件是 UTF-8：
  读取时把 UTF-8 字节按 GBK 解释，写回时再编码成 UTF-8，形成**双重编码**。
- 更关键的是：**CP936 解码器对无法映射的字节输出 `?`（0x3F）**，因此每个三字节汉字的
  最后一个字节被替换成了 `?`，该字节的信息在那一刻被销毁。

## 2. 恢复做了什么

1. **逆向双重编码**：用 CP936 字符到字节的反查表把损坏文本还原成"原始 UTF-8 字节流"，
   再用严格 UTF-8 解码。绝大部分中文由此正确还原。
2. **补回丢失的尾字节**：还原后全文剩 326 处 `?`。每一处都落在"某个字的最后一个字节"位置上；
   用该字剩余字节作词干、枚举合法尾字节（0x80–0xBF）、按中文标点常用度选定候选补齐。
3. **修复由此产生的语法破损**：损坏把"某个字的尾字节 + 字符串收尾单引号"一起吞掉时会造成
   字符串未闭合；共修复 64 行未闭合字符串与若干语法错误，直到 ArkTS 编译通过。
