### A3. 数据与状态机

新增 `model/GarmentImport.ets` 或放入现有合适模型文件；不要把 UI 组件作为服务层类型依赖。建议最小结构：

```typescript
enum ImportPhase { WAITING, COPYING, READY, CUTTING, SAVING, SAVED, ERROR, SKIPPED }
enum ImportFailureStep { NONE, COPY, CUTOUT, SAVE }

interface ImportItem {
  id: string;                  // 任务 ID，选图时创建，重试不变
  garmentId: string;           // 将来入库的 ID，选图时创建，重试不变
  sourceUri: string;           // Picker URI，仅当前会话，不写衣橱快照
  originalUri: string;         // 归当前任务拥有的沙箱原图
  cutoutUri: string;           // 可空，同样属于当前任务
  useCutout: boolean;
  phase: ImportPhase;
  failureStep: ImportFailureStep;
  error: string;
  draft: ImportGarmentDraft;   // 每项独立对象，含 name/category/color/温度/场合
  revision: number;            // 使过期异步结果失效
}
```

`ImportGarmentDraft` 保存 `categoryIndex = -1` 的未确认状态、温度是否经用户修改等必要字段。具体 enum 写法要符合项目 ArkTS 编译器，以上不是可跳过编译验证的成品代码。

推荐状态转换：

```text
WAITING → COPYING → READY
                ↘ ERROR(COPY) → COPYING
READY → CUTTING → READY
              ↘ ERROR(CUTOUT) → READY(选择原图) / CUTTING(重试)
READY → SAVING → SAVED
             ↘ ERROR(SAVE) → SAVING(同 ID 重试)
未保存且非 SAVING → SKIPPED(确认放弃，失效在途结果并清理)
```

保存前必须满足：有成功解码并显示的本地图片、名称合法、品类已确认、温度有限且在表单范围内、最低不高于最高、至少一个有效场合。抠图失败但原图存在时允许明确选择原图保存。

状态所有者只有一个，建议父页面持有数组和异步任务，子页接收值与回调。修改数组元素时生成新对象/新数组，让 ArkUI V1 能观察变化。禁止全队列共用一个 `@Link draft` 导致切项串数据。

1. 在仓储拆出“选择多张 URI”和“导入一张 URI”；单件编辑的 `chooseImage` 可调用同一底层导入函数，保持原接口。

4. 输入延续 20 MB 限制。读取 ImageInfo 后再创建缩小后的 PixelMap，建议最长边 2048，按比例缩放且不放大小图；本地预算明确拒绝超过 4000 万像素的输入。这是产品资源预算，不是声称华为 API 的硬限制。
5. 建议将导入结果统一编码为 PNG，保留透明通道，扩展名与编码一致；不能把 PNG 字节直接命名成 JPG。验收含竖拍 JPEG 的方向和透明 PNG，方向处理按实际 SDK 合同核对。

7. 打开文件、ImageSource、PixelMap、ImagePacker 均明确归属，成功、失败、取消均释放；一个释放失败不能跳过其余清理。失败的半成品删除。
8. 使用 session ID 与 item revision 判定回调是否仍有效。离开流程或替换图片后到达的旧结果只能清理，不得重开页面、覆盖新项或弹成功提示。

10. 抠图全局最多同时一个原生任务，复用 `GarmentCutout`。不要让单件编辑与批量任务重叠占用同一服务；旧任务未结束前禁止启动第二个原生任务，不能把取消标记当成底层服务真的终止。
11. 文件清理只能针对本应用生成、当前任务拥有、且未被持久化衣物或其他记录引用的文件。禁止删除 Picker 的原始相册 URI。

| 时机 | 可以清理 | 必须保留 |
| --- | --- | --- |
| 抠图失败 | 本次未完成输出 | 原图及其他任务图片 |

### A5. 保存必须有明确的成功边界

当前 `addGarment` 会先修改内存、关闭表单、提示成功，再异步 `persist`；批量流程不能照抄。新接口应返回 `Promise`，等待仓储保存成功后才移交图片所有权、增加已保存数、允许进入下一件。

建议做一个局部的衣物提交方法，新增与现有单件编辑共用：

```text
校验输入和容量
→ 设置提交锁，构造带稳定 garmentId 的候选衣物
→ 基于父层当前快照构造 candidate，尚不发布“已保存”状态
→ await repository.save(candidate)
→ 成功：合并该 ID 到父状态，标记该任务 SAVED，刷新推荐/卡片
→ 失败：保持当前项与输入图片，显示当前项保存错误
→ finally：解除提交锁，处理等待的刷新
```

必须解决与天气、卡片唤起和其他 `persist` 调用的交错；只有仓储写队列并不保证调用方先生成的全量快照不会覆盖新数据。

本阶段建议采用短暂的父层提交锁：

- SAVING 期间禁用表单变更、重复提交、任务切换以及离开该流程；顶部返回与系统返回同样处理。
- 可能改变快照的异步天气结果等延后应用；卡片唤起延后导航，不删除正在保存的草稿。
- 此期间 `persist` 请求记录为“需要补存”，不把旧快照放进仓储队列。
- 保存结束，先发布成功结果或保留失败草稿，再应用待处理的外部变更；需要补存时用此时最新的完整状态保存。
- 不覆盖或删除原有衣物、收藏、日记、城市、档案字段；不要通过 `restore(candidate)` 把运行中的其他状态回退。
- 每个任务 ID 幂等：已成功的同一 `garmentId` 重试不会追加第二件；100 件限制只拦新增，不拦编辑和幂等确认。
- 单件编辑更换图片：旧图至少保留到新快照成功，失败时原衣物仍可显示。

实现时检索所有直接 `repository.save` 调用，不能只拦住 `persist` 却遗漏另一个写入口；覆盖与此提交流程能够实际交错的路径即可。失败注入至少包含一次“磁盘保存被延迟时天气回调到达”的执行测试，不能仅凭按钮禁用推断无并发。

锁只覆盖一次实际磁盘提交，不覆盖用户填写表单的时间；不要新增覆盖全应用的复杂状态框架。

## 4. 任务 B：明确偏好与近期穿着排序

只有 A 的构建、数据测试与 UI 主流程完成后再实施 B。

### B1. 产品语义先固定

第一版反馈粒度是“某件衣物”。在衣物详情和搭配详情展开的单品操作区提供三个互斥状态：多推荐、默认、少推荐。使用与当前系统图标一致的选择控件和可访问性标签。

“少推荐”仅降排序，不是排除、归档或待洗；“多推荐”不能越过温度、场合、可穿状态和排除条件。用户明确锁定的衣物优先遵守锁定；锁定与不可穿条件冲突仍返回原有解释。

收藏仍表示保存作品，不隐式批量点赞其中所有衣物；日记里的“偏热/偏冷/不舒服”不自动改温度区间，不猜是哪一件导致。现阶段只从日记/穿着记录提取最近穿过的日期。

不增加“这套不喜欢”按钮，避免把组合不喜欢错误分摊到每一件单品。组合级偏好留作后续独立决策。

### B2. 数据与兼容

- `Garment` 新增可选字段 `recommendationPreference?: number`，仅允许 -1、0、1。旧数据缺少字段按 0；新字段非法则局部恢复为 0，不丢整个快照。
- `copyGarment` 必须保留该字段；新增衣物显式 0；修改颜色、图片、状态等操作不能把偏好清掉。
- 不增加独立累计计分表，重复点击“多推荐”就是 1，不累加；切换回默认就是 0。
- 原 `version: 1` 与文件名继续使用，迁移补默认值，不能重置示例库。
- 可新增 `RecommendationContext`，包含只读的 diary、records、today。本机日历日期在调用方生成，纯排序函数不读 `Date.now()`，便于固定日期验收。
- 推荐上下文可作为函数第三个可选参数传入，默认空历史以兼容旧调用。真正推荐/替换入口必须显式传当前上下文；`eligible` 和卡片的有效性判断不依赖历史。

### B3. 精确排序规则

先完成原有硬过滤和锁定校验，再对每个品类候选使用同一个比较器，逐项比较：

1. `recommendationPreference` 降序：1、0、-1。
2. 原 `preferenceScore` 降序。
3. `recentWearPenalty` 升序。
4. `wearCount` 升序。
5. 衣物 ID 按确定的字符串顺序升序，作为稳定的最终平手规则。

不改成任意权重加总，也不增加随机打乱。先把此规则完整落地，后续有使用数据再调优。

最近穿着日期取 diary 与 records 的联合：对每个衣物 ID 取有效日期最大值。两处记录同一次穿着不会重复罚分，因为只取最近一天，不按条数求和。

日期先按现有 `normalizedDay` 兼容旧格式，再验证是真实日历日期。使用日历日序号比较，不用 `new Date('YYYY-MM-DD')` 加本地时区，不用两个本地午夜时间戳除 86400000 处理跨夏令时。

| 距 today 的日历日差 | 罚分 |
| --- | --- |
| 0 | 6 |
| 1 | 4 |
| 2–3 | 2 |
| 4–6 | 1 |
| ≥7 或无有效历史 | 0 |

未来日期、非法日期、未知衣物 ID 不参与。所有输入数组保持不变。建议先一次性构造最近日期索引，比较器内不重复扫描全部日记。

“无历史”不能解释成“从未穿过”，因为旧记录有限；只可说“近期暂无记录”。少推荐如果是该品类唯一合法候选，仍然返回它，说明“当前条件下可选单品较少”。

保留最多三套、组合去重和品类需求规则。本轮是候选排序升级，不宣称返回全局最优三套组合；不要无界枚举全部笛卡尔积。

### B4. 必须同时处理的接线点

| 入口 | 需要接入 |
| --- | --- |
| `Index.request/regenerate` | 当前偏好、日期、日记与 records；反馈成功后重新计算 |
| `Index.replace` | 同一比较器与上下文 |
| `OutfitDetailPage.request` | 当前真实档案与历史，不再始终 `emptyProfile`；上下文用当前工作方案的温度/场合 |
| `OutfitStudioPage.autoFill` | 当前真实档案与历史；只影响一键搭配，不重排用户已经手工摆放的画布 |
| `copyGarment`、保存/恢复、新增/编辑/状态变化 | 不丢新偏好字段 |
| 首页和搭配推荐卡 | 同一批排序结果；理由由实际排序因素产生 |
| `CardData` | 仅保持有效性校验，少推荐不能令当前卡片无效 |

重点：当前 `regenerate()` 会把 `activeIds` 对应方案重新移到第一位。新增排序若忽略此处，结果会被旧方案覆盖。

建议给 `regenerate` 增加明确选项 `preserveActive`，默认 true；用户主动修改推荐偏好、主动重新推荐时传 false，接受新排序并令 `activeIds` 指向新的第一套，再保存和更新卡片。恢复旧快照、普通导航返回仍沿用保留当前方案的规则。不允许永远无条件 `unshift` 旧方案。

保存偏好使用 A 阶段已经验证的提交边界；只有落盘成功才提示“已设为少推荐”并刷新排序。保存失败保持原偏好和原推荐，可重试；不要制造内存偏好与磁盘不同的假成功。

具体提交时，先在候选状态中计算新偏好对应的推荐和新 `activeIds`，将衣物偏好与新 `activeIds` 一起写入同一份快照，成功后发布到 UI。不要先保存偏好，再仅在内存改 `activeIds`，否则重启又会把旧方案置顶。卡片更新使用这次已落盘的方案。

日记新增/删除后重建历史索引；在前台恢复或下一次发起推荐时更新 `today`，跨过午夜不需要用户重启应用才能重新计算。

### B5. 推荐理由

原来的温度、场合与状态理由保留，可追加一条确有证据的简短信息，例如“优先考虑你标记为多推荐的蓝色衬衫”。不要在界面展示分数公式、字段名、算法实现说明，不使用“AI 学会了你的风格”等文案。

缺少个人历史时正常推荐，不产生假历史。不修改旧收藏里已保存的历史理由和用户画布；刷新的是新推荐方案。
