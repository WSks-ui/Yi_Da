# ArkUI 与多设备界面

> 导航入口：[ArkUI 组件参考](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/arkui-overview) · [布局开发](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/arkts-layout-development) · [一次开发，多端部署](https://developer.huawei.com/consumer/cn/best-practices/multidevice/)

组件 API、属性可用级别和导航能力需按项目 SDK 实时核验。本文件用于设计与验证，不提供可盲贴的固定 API 签名。

## 先建立界面约束

- 目标设备、窗口尺寸、横竖屏、折叠状态和输入方式。
- 最低兼容 API 与项目当前导航、状态管理和资源体系。
- 内容密度、无障碍、字体缩放、主题、语言方向和多语言长度。
- 加载、空、错误、无权限、离线和部分数据状态。

## 组件与布局

- 优先复用项目现有组件、主题 token、间距和资源。
- 使用 `Column`、`Row`、`Flex`、`Grid`、`List`、`Stack` 等容器时，明确父子约束与滚动所有权。
- 列表数据较大时核对懒加载组件的数据源、稳定 key、复用和更新契约。
- 避免把单一屏幕宽高、固定文本长度或鼠标交互当作所有设备的前提。
- 使用资源引用承载用户可见文本、颜色、图标和可本地化内容。
- 导航、弹窗和菜单沿用项目现有范式；核对当前 API 是否已替代旧接口。

## 响应式与多设备

- 从实际断点或窗口能力推导布局，不默认设备一定是 PC、手机或平板。
- 在布局变化时保持业务状态稳定，避免为每个断点复制完整页面逻辑。
- 检查键盘、鼠标、触控、焦点、返回动作和窗口缩放的差异。
- 对能力受限设备，用 SysCap/API/设备约束提供降级，而不是依赖运行时崩溃。

## 交互与无障碍

- 可交互元素应有可理解标签、正确状态和足够触达区域。
- 不仅用颜色表达错误、选中或风险。
- 焦点顺序应与视觉和操作顺序一致。
- 动画服务于状态变化；处理减少动态效果、打断、重复触发和页面离开。
- 删除、支付、权限等高影响操作需要清晰反馈和可恢复边界。

## 性能与生命周期

- 避免在 `build()` 路径执行 I/O、重计算或产生不稳定对象。
- 大列表、图片、复杂绘制和高频状态更新先测量再优化。
- 控制器、监听、定时器和异步任务要有明确所有者与释放点。
- 页面离开后，异步回调不能继续写入已销毁或已替换的 UI 状态。

## 验证矩阵

按任务范围选择：

- 目标设备与关键窗口尺寸。
- 横竖屏、深浅色、字体缩放、多语言。
- 首次进入、返回、恢复、重复进入。
- 加载、空、错误、无权限、离线。
- 键盘/鼠标/触控/焦点。
- 真机或模拟器；无法运行时明确未验证项。
