# 性能诊断与优化

> 导航入口：[HarmonyOS 应用开发最佳实践](https://developer.huawei.com/consumer/cn/best-practices/) · [开发者测试服务](https://developer.huawei.com/consumer/cn/testing/get-started/)

性能结论应来自复现场景、测量和代码路径。不要把固定帧率、耗时、内存增长、函数长度或组件层级阈值当作跨项目事实。

## 诊断流程

1. 固定设备、系统/API、构建类型、数据规模和操作步骤。
2. 明确症状：启动慢、掉帧、卡顿、内存增长、耗电、网络慢或包体积。
3. 获取基线：官方 Profiler、AppAnalyzer、测试服务、trace、日志或项目 benchmark。
4. 将热点映射到具体函数、状态更新、I/O、分配、渲染或网络调用。
5. 做最小修改，用同一场景前后对比。
6. 报告收益、方差、设备限制和未覆盖场景。

## 常见代码路径

### 渲染与状态

- `build()` 或高频回调中的 I/O、解析、排序、对象创建和重复计算。
- 过宽状态依赖导致无关 UI 更新。
- 大集合未使用适合的懒加载/虚拟化契约，或 key 不稳定。
- 高频事件直接写状态，缺少合并、节流或最小更新。
- 图片尺寸、解码和缓存策略与显示尺寸不匹配。

### 启动

- 首屏前串行初始化非关键服务。
- 模块加载、数据库迁移、配置解析和网络请求阻塞首个可交互状态。
- “延迟初始化”仍需生命周期和任务优先级依据；不要用任意 `setTimeout` 伪装优化。

### 内存与资源

- 监听、定时器、控制器、`ResultSet`、文件、HTTP、Socket、媒体对象和 Worker 未释放。
- 缓存没有容量、淘汰或数据生命周期边界。
- 页面退出后任务与闭包继续持有组件或大对象。
- 重复进入页面导致订阅、缓存或后台任务累积。

### 网络与存储

- 主线程敏感路径执行同步或大块 I/O。
- 重复请求、无界响应、全量读写或不必要序列化。
- 缓存缺少一致性、失效、容量和敏感数据策略。
- 并发优化改变顺序、原子性或错误语义。

## 优化原则

- 优先消除已测得的主导瓶颈。
- 保留正确性、错误传播、取消和资源清理语义。
- 不凭直觉把串行改成并行；先确认依赖、并发上限和失败策略。
- 不用降低画质、无障碍或数据一致性换取未量化收益。
- 当只能做代码审计时，将结论表述为“可预测的昂贵路径”，并说明缺少的运行时证据。

## 验证

- 同设备、同构建、同数据、同操作，多次运行并记录波动。
- 覆盖冷启动/热启动、首次/重复进入、前后台和资源释放后的稳定状态。
- 对 UI 记录帧与响应，对内存观察回落与长期趋势，对网络区分客户端与服务端时间。
- 无真机或工具时，不声称达到性能目标，只报告静态修改和未验证边界。
